# Vacation Request App

Небольшое full-stack приложение для создания и согласования заявок на отпуск.

## Возможности

- создание заявки на отпуск;
- валидация входных данных на backend;
- автоматический расчёт количества календарных дней;
- просмотр списка заявок;
- фильтрация по статусу;
- одобрение заявки;
- отклонение заявки с обязательной причиной;
- отображение причины отклонения;
- обработка ошибок API;
- защита UI от повторных запросов.

## Стек

- Node.js
- Express
- Vanilla HTML
- CSS
- JavaScript
- Node.js Test Runner

Дополнительные frontend-фреймворки, база данных и ORM не используются.

## Запуск тестов

```bash
npm test
```

Тесты используют встроенный `node:test`, поэтому дополнительные тестовые библиотеки не требуются.

Проверяются основные сценарии:

* успешное создание заявки;
* корректный расчёт количества дней;
* ошибка при `endDate < startDate`;
* одобрение заявки;
* запрет отклонения без причины;
* запрет повторного изменения финального статуса;
* фильтрация по статусу.

## Как пользоваться приложением

1. Заполнить ФИО сотрудника.
2. Выбрать дату начала отпуска.
3. Выбрать дату окончания отпуска.
4. Указать причину.
5. Нажать кнопку отправки заявки.
6. Новая заявка появится в списке со статусом `Ожидает`.
7. Заявку можно одобрить или отклонить.
8. При отклонении необходимо указать причину.
9. Список заявок можно фильтровать по статусу.

## Хранение данных

Данные хранятся в памяти процесса Node.js.

Это означает, что после перезапуска сервера все созданные заявки удаляются.

Для данного тестового задания такое хранение используется намеренно, чтобы не добавлять лишнюю инфраструктуру и базу данных.

## Модель заявки

Пример заявки:

```json
{
  "id": "uuid",
  "employeeName": "Иван Иванов",
  "startDate": "2026-09-10",
  "endDate": "2026-09-12",
  "reason": "Семейная поездка",
  "status": "pending",
  "days": 3,
  "rejectionReason": null,
  "createdAt": "2026-09-09T12:00:00.000Z"
}
```

Возможные статусы:

* `pending`
* `approved`
* `rejected`

На frontend статусы отображаются на русском языке:

* `pending` — Ожидает
* `approved` — Одобрена
* `rejected` — Отклонена

## API

### Получить заявки

```http
GET /api/requests
```

Получить заявки с определённым статусом:

```http
GET /api/requests?status=pending
```

Допустимые значения:

```text
pending
approved
rejected
```

### Создать заявку

```http
POST /api/requests
Content-Type: application/json
```

Пример тела запроса:

```json
{
  "employeeName": "Иван Иванов",
  "startDate": "2026-09-10",
  "endDate": "2026-09-12",
  "reason": "Семейная поездка"
}
```

При успешном создании сервер возвращает:

```text
201 Created
```

### Одобрить заявку

```http
PATCH /api/requests/:id/approve
```

Одобрить можно только заявку со статусом `pending`.

### Отклонить заявку

```http
PATCH /api/requests/:id/reject
Content-Type: application/json
```

Пример тела:

```json
{
  "reason": "Период не согласован"
}
```

Причина отклонения обязательна.

Отклонить можно только заявку со статусом `pending`.

## Валидация

Backend является источником истины и самостоятельно проверяет входящие данные.

При создании заявки:

* ФИО обязательно;
* дата начала обязательна;
* дата окончания обязательна;
* даты должны иметь корректный формат;
* дата окончания не может быть раньше даты начала;
* причина отпуска обязательна.

При отклонении заявки причина отклонения обязательна.

HTML validation на frontend используется только как дополнительный UX-слой.

## Расчёт количества дней

Количество дней рассчитывается на backend.

Диапазон дат включительный.

Например:

```text
2026-09-10 — 2026-09-10 = 1 день
2026-09-10 — 2026-09-12 = 3 дня
```

Для расчётов календарные даты обрабатываются через UTC, чтобы результат не зависел от локальной временной зоны сервера.

## Ошибки API

Пример ошибки валидации:

```json
{
  "error": "Validation error",
  "details": {
    "endDate": "Дата окончания не может быть раньше даты начала"
  }
}
```

Основные HTTP-коды:

* `200` — успешный запрос;
* `201` — заявка создана;
* `400` — некорректные входные данные;
* `404` — заявка не найдена;
* `409` — заявка уже обработана.

## Основные архитектурные решения

### Backend — источник истины

Frontend не хранит заявки в `localStorage` и не рассчитывает бизнес-состояние самостоятельно.

После создания, одобрения или отклонения заявки frontend повторно загружает данные через REST API.

### In-memory storage

Для тестового задания используется простое хранилище в памяти.

Это позволяет сохранить реализацию небольшой и сосредоточиться на REST API и бизнес-логике.

### Безопасная работа с календарными датами

Значения вида `YYYY-MM-DD` не преобразуются через локальную временную зону.

Для расчёта продолжительности используются UTC-компоненты даты.

### Минимальные зависимости

В runtime используется только Express.

Для тестов применяется встроенный в Node.js test runner.

## Ограничения

Проект сделан как небольшое тестовое приложение, поэтому:

* данные не сохраняются после перезапуска сервера;
* нет авторизации и ролей пользователей;
* нет базы данных;
* нет пагинации;
* нет production-конфигурации деплоя.
